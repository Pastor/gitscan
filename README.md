# gitscan

Утилита для ведения локального зеркала репозиториев GitHub-аккаунта.

Изначально `gitscan` рекурсивно находил `.git`-каталоги и обновлял их
(`fetch --all --tags`, `pull --all`, `submodule update`). Этот режим остался — команда `scan`.
Поверх него добавлены получение списка репозиториев через GitHub API, клонирование
отсутствующих, полная синхронизация веток/тегов/подмодулей, актуализация форков
из upstream и реестр репозиториев.

Зависимостей нет — только стандартная библиотека Go.

## Сборка

```sh
go build -o gitscan .
```

## Команды

```sh
gitscan                 # полная синхронизация + пересборка реестра
gitscan scan            # старое поведение: обновить всё, что лежит в папке, без GitHub API
gitscan registry        # только пересобрать реестр по локальному состоянию
gitscan list            # что есть на GitHub, ничего не меняя
gitscan token           # где найден токен и работает ли он
gitscan -h              # все флаги
```

Флаг `-scan_dir` сохранён как синоним `-dir` для совместимости.

## Структура папки

```
<папка>/
├── repositories/<репозиторий>/   сами репозитории (имя папки меняется флагом -repos)
├── REGISTRY.md                   реестр для чтения
├── registry.json                 реестр машиночитаемый
├── registry.csv                  сводная таблица репозиториев
├── registry-branches.csv         таблица всех веток
├── .sync/                        кэши GitHub API, кэш реестра, логи, token, .env
└── __broken/                     карантин повреждённых копий
```

Каталоги, начинающиеся с точки или с `__`, при обходе пропускаются —
соглашение из исходной версии.

## Что делает синхронизация

1. Забирает список репозиториев: с токеном — `/user/repos` (включая приватные),
   без токена — публичный список. Как и на странице профиля, включаются чужие
   репозитории, где пользователь участник (`-member=false` отключает).
2. Новые репозитории клонирует целиком, затем дотягивает все теги и заводит
   локальные ветки под каждую ветку `origin`.
3. Существующие обновляет: `fetch origin --prune --tags "+refs/heads/*:refs/remotes/origin/*"`.
   Текущая ветка двигается только `merge --ff-only` и только при чистой рабочей копии,
   остальные — через `update-ref` и только вперёд. Разошедшиеся ветки не трогаются,
   а отмечаются в реестре. `--force` не используется нигде.
4. Неполные (shallow) копии дотягиваются до полной истории.
5. Подмодули обновляются отдельным шагом: недоступный подмодуль не срывает клонирование.
6. Повреждённые копии (оборванный клон, битый `.git`, зависший `config.lock`) уезжают
   в `__broken/<имя>-<дата>` и клонируются заново — данные не удаляются.
7. Пересобирается реестр.

Ничего локального не удаляется: репозиторий, исчезнувший с GitHub, остаётся на диске,
о нём появляется строка в логе.

## Форки

Для каждого форка определяется исходный репозиторий (`parent` через GitHub API,
кэш в `.sync/parents.json`), заводится remote `upstream` и дальше:

- **локально** — ветки форка, отставшие от одноимённых веток upstream, перематываются вперёд;
- **на GitHub** — те же ветки обновляются через API `merge-upstream` (кнопка «Sync fork»);
  если API отказал — обычный `git push origin` без `--force`;
- разошедшиеся ветки не трогаются и попадают в реестр как `+N / −M`.

Флаги: `-fork-sync=false`, `-fork-push=false`, `-fork-tags`.

## Реестр

`REGISTRY.md` — сводные таблицы (свои / форки / чужие с участием) и раздел по каждому
репозиторию: описание (из GitHub, иначе из README), ветка по умолчанию, таблица веток
с расхождением относительно ветки по умолчанию и относительно upstream, теги, подмодули,
размер на диске, пометки о незакоммиченных изменениях.

`registry.json` — то же машиночитаемо, с полными списками веток и тегов.
`registry.csv` и `registry-branches.csv` — плоские таблицы (с BOM, чтобы Excel не ломал кириллицу).

Описание каждого репозитория кэшируется по отпечатку всех ref-ов, поэтому повторная
сборка реестра быстрая. Флаг `-registry-budget 30s` ограничивает время пересборки:
что не успело — обновится при следующем запуске.

## Токен GitHub

Нужен для приватных репозиториев, обновления форков на GitHub и чтобы не упираться
в лимит API (60 запросов в час без токена против 5000 с ним).

Порядок поиска:

1. флаг `-token`
2. переменные окружения `GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_PAT`, `GH_PAT`,
   `GITHUB_ACCESS_TOKEN`, `PASTOR_SYNC_TOKEN`
3. файлы `.env` — путь из `-env`, затем `<папка>/.env`, `<папка>/.sync/.env`,
   `./.env`, `~/.env`, `~/.config/pastor-sync/.env`
4. файлы с «голым» токеном: `<папка>/.sync/token`, `~/.github_token`

```env
# .env
GITHUB_TOKEN=ghp_xxxxxxxxxxxx
GITHUB_USER=Pastor
```

`gitscan token` покажет, какие места проверены, откуда взят токен (замаскированным),
кем вас видит GitHub, права токена и остаток лимита.

Токен не попадает ни в `.git/config`, ни в командную строку: git получает его через
временный `GIT_ASKPASS`-хелпер, который удаляется по завершении работы.

## Права токена

- классический токен: область `repo`;
- fine-grained: Repository permissions → Contents: Read and write
  (write нужен только для обновления форков).
