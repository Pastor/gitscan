# gitscan

Утилита для ведения локального зеркала репозиториев: аккаунт GitHub
и любое число инстансов GitLab (в том числе собственных).

Изначально `gitscan` рекурсивно находил `.git`-каталоги и обновлял их
(`fetch --all --tags`, `pull --all`, `submodule update`). Этот режим остался — команда `scan`.
Поверх него добавлены получение списка репозиториев через API GitHub и GitLab, клонирование
отсутствующих, полная синхронизация веток/тегов/подмодулей, актуализация форков
из upstream и реестр репозиториев.

Зависимостей нет — только стандартная библиотека Go.

## Сборка

```sh
go build -o gitscan .
```

## Команды

```sh
gitscan                 # полная синхронизация всех источников + пересборка реестра
gitscan -source work    # только источник work (можно несколько через запятую)
gitscan scan            # старое поведение: обновить всё, что лежит в папке, без API
gitscan registry        # только пересобрать реестр по локальному состоянию
gitscan list            # что есть на серверах, ничего не меняя
gitscan token           # где найдены токены и работают ли они
gitscan sources         # настроенные источники
gitscan source add -name work -url https://git.company.ru -token glpat-...
gitscan source remove work
gitscan -h              # все флаги
```

`-only` ищет подстроку в полном пути `<источник>/<путь>`, например `-only work/infra/`.

## Источники

Источники описываются в `<папка>/gitscan.json` (другой путь — флаг `-config`).
Если файла нет, источник один — GitHub, как в версиях 1.x. Пример со всеми
параметрами — [gitscan.example.json](gitscan.example.json).

```json
{
  "sources": [
    { "name": "github", "type": "github", "user": "Pastor" },
    { "name": "work", "type": "gitlab", "url": "https://git.company.ru",
      "token_env": "WORK_GITLAB_TOKEN", "jobs": 4 }
  ]
}
```

| Параметр | Что значит |
|---|---|
| `name` | имя источника, оно же каталог в `repositories/` |
| `type` | `github` или `gitlab` |
| `url` | адрес инстанса; можно с подкаталогом (`https://host/gitlab`). Для github.com не нужен, для GitHub Enterprise — адрес сервера |
| `user` | GitHub: чьи репозитории. В GitLab пользователь определяется по токену |
| `token_env`, `token_file` | где взять токен (см. ниже). Сам токен в конфиг не пишется |
| `scope` | GitLab: `membership` (по умолчанию: все проекты, где вы участник), `owned` (только личные), `all` (всё, что видно токену, у администратора — весь инстанс) |
| `groups` | GitLab: только эти группы вместе с подгруппами, вместо `scope` |
| `ca_file` | корневой сертификат инстанса (PEM) для самоподписанных сертификатов. Действует и на API, и на git, но только для адресов этого источника |
| `insecure` | не проверять TLS-сертификат. Лучше указать `ca_file` |
| `ssh` | клонировать этот источник по ssh (иначе как флаг `-ssh`) |
| `jobs` | не больше N одновременных операций с этим сервером |
| `disabled` | пропускать источник, пока он не указан явно в `-source` |

`gitscan source add` создаёт `gitscan.json`, если файла ещё нет, и переносит в него
прежний GitHub-источник. Токен из `-token` записывается в
`<папка>/.sync/tokens/<имя>` с правами 0600. После добавления токен сразу проверяется.

## GitLab

Через API забирается список проектов: keyset-пагинация, поэтому инстансы на десятки
тысяч проектов тоже работают. Дальше каждый проект синхронизируется так же, как
репозиторий GitHub (см. ниже).

- Проекты с выключенным репозиторием пропускаются.
- Пустые проекты клонируются без ошибки.
- Проекты, помеченные к удалению, синхронизируются и отмечаются в реестре: локальная копия останется.
- Если проект переименовали или перенесли в другую группу, локальная копия переезжает
  следом (по ID проекта), а не клонируется заново.
- Форки определяются и попадают в реестр, но их синхронизация с upstream пока
  работает только для GitHub.

Права токена: `read_api` и `read_repository`.

Флаг `-scan_dir` сохранён как синоним `-dir` для совместимости.

## Структура папки

```
<папка>/
├── gitscan.json                  источники (необязательный)
├── repositories/<источник>/<путь>/   сами репозитории (имя папки меняется флагом -repos),
│                                 например repositories/github/Pastor/gitscan,
│                                 repositories/work/platform/backend/app
├── REGISTRY.md                   реестр для чтения
├── registry.json                 реестр машиночитаемый
├── registry.csv                  сводная таблица репозиториев
├── registry-branches.csv         таблица всех веток
├── .sync/                        кэши API по источникам (sources/<имя>/), токены (tokens/), кэш реестра, логи, .env
└── __broken/                     карантин повреждённых копий
```

Каталоги, начинающиеся с точки или с `__`, при обходе пропускаются —
соглашение из исходной версии.

**Переход с 1.x.** Репозитории старой плоской раскладки (`repositories/<имя>`) при первом
запуске сами переносятся в `repositories/<источник>/<владелец>/<имя>`. Источник
определяется по адресу `origin`. Перенос делается через `rename`, данные не копируются
и не удаляются. Посмотреть план без изменений можно через `gitscan -dry-run`.

## Что делает синхронизация

1. Для каждого источника забирает список репозиториев. GitHub: с токеном — `/user/repos` (включая приватные),
   без токена — публичный список. Как и на странице профиля, включаются чужие
   репозитории, где пользователь участник (`-member=false` отключает).
2. Новые репозитории клонирует целиком, затем дотягивает все теги и заводит
   локальные ветки под каждую ветку `origin`.
3. Существующие обновляет: `fetch origin --prune --tags "+refs/heads/*:refs/remotes/origin/*"`.
   Текущая ветка двигается только `merge --ff-only` и только при чистой рабочей копии,
   остальные — через `update-ref` и только вперёд. Разошедшиеся ветки не трогаются,
   а отмечаются в реестре. `--force` не используется нигде.
4. Неполные (shallow) копии дотягиваются до полной истории.
5. Подмодули обновляются отдельным шагом: недоступный подмодуль не срывает клонирование.
6. Повреждённые копии (оборванный клон, битый `.git`, зависший `config.lock`) уезжают
   в `__broken/<имя>-<дата>` и клонируются заново — данные не удаляются.
7. Пересобирается реестр.

Ничего локального не удаляется: репозиторий, исчезнувший с сервера, остаётся на диске,
о нём появляется строка в логе.

## Форки

Для каждого форка определяется исходный репозиторий (`parent` через GitHub API — только для GitHub-источников,
кэш в `.sync/sources/<имя>/parents.json`), заводится remote `upstream` и дальше:

- **локально** — ветки форка, отставшие от одноимённых веток upstream, перематываются вперёд;
- **на GitHub** — те же ветки обновляются через API `merge-upstream` (кнопка «Sync fork»);
  если API отказал — обычный `git push origin` без `--force`;
- разошедшиеся ветки не трогаются и попадают в реестр как `+N / −M`.

Флаги: `-fork-sync=false`, `-fork-push=false`, `-fork-tags`.

## Реестр

`REGISTRY.md` — разделы по источникам со сводными таблицами (свои / форки / чужие или
групповые) и раздел по каждому
репозиторию: описание (из GitHub, иначе из README), ветка по умолчанию, таблица веток
с расхождением относительно ветки по умолчанию и относительно upstream, теги, подмодули,
размер на диске, пометки о незакоммиченных изменениях.

`registry.json` — то же машиночитаемо, с полными списками веток и тегов. Начиная с
версии 2.0 в нём есть поле `schema: 2`, список `sources`, а у каждого репозитория — `key`
(`<источник>/<путь>`), `source` и `provider`.
`registry.csv` и `registry-branches.csv` — плоские таблицы (с BOM, чтобы Excel не ломал кириллицу).

Описание каждого репозитория кэшируется по отпечатку всех ref-ов, поэтому повторная
сборка реестра быстрая. Флаг `-registry-budget 30s` ограничивает время пересборки:
что не успело — обновится при следующем запуске.

## Токены

У каждого источника свой токен. Порядок поиска:

1. `token_env` из конфига — переменная окружения, затем файлы `.env` (список ниже);
2. `token_file` из конфига;
3. `<папка>/.sync/tokens/<имя>` — сюда пишет `gitscan source add -token`;
4. основной GitHub-источник — старые места (ниже), остальные — переменная
   `GITLAB_TOKEN_<ИМЯ>` (`GITLAB_TOKEN_WORK` для источника `work`) в окружении или `.env`.

### Основной GitHub-источник

Токен нужен для приватных репозиториев, обновления форков на GitHub и чтобы не упираться
в лимит API (60 запросов в час без токена против 5000 с ним).

Порядок поиска:

1. флаг `-token`
2. переменные окружения `GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_PAT`, `GH_PAT`,
   `GITHUB_ACCESS_TOKEN`, `PASTOR_SYNC_TOKEN`
3. файлы `.env` — путь из `-env`, затем `<папка>/.env`, `<папка>/.sync/.env`,
   `./.env`, `~/.env`, `~/.config/pastor-sync/.env`
4. файлы с «голым» токеном: `<папка>/.sync/token`, `~/.github_token`

```env
# .env
GITHUB_TOKEN=ghp_xxxxxxxxxxxx
GITHUB_USER=Pastor
```

`gitscan token` покажет, какие места проверены, откуда взят токен (замаскированным),
кем вас видит GitHub, права токена и остаток лимита.

Токен не попадает ни в `.git/config`, ни в командную строку: git получает его через
временный `GIT_ASKPASS`-хелпер, который удаляется по завершении работы. Хелпер отдаёт
токен только хостам своего источника. Поэтому токен GitHub не уйдёт на GitLab, а токен
GitLab не уйдёт на сервер чужого подмодуля. Для адресов источника с токеном отключается
системное хранилище паролей git (osxkeychain и т. п.): токен в него не сохраняется,
а устаревший пароль оттуда не подменяет токен.

## Права токена

- классический токен: область `repo`;
- fine-grained: Repository permissions → Contents: Read and write
  (write нужен только для обновления форков).
